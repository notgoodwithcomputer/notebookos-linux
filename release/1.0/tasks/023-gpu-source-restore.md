## 1. Source-tree finding and restore accounting

The premise that `kbuild-desktop/` is an in-tree source copy is not true of the tree on disk at execution time. `kbuild-desktop/Makefile` is a 228-byte generated wrapper containing:

```make
# Automatically generated by /home/ben/Documents/notebookos-linux/linux/Makefile: don't edit
export KBUILD_OUTPUT = /home/ben/Documents/notebookos-linux/kbuild-desktop
include /home/ben/Documents/notebookos-linux/linux/Makefile
```

Thus `kbuild-desktop/` is an **out-of-tree object directory**, and its `drivers/gpu/drm/amd` and `nouveau` directories contain generated objects, not source. The compiler log confirms source rules came from `/home/ben/Documents/notebookos-linux/linux/scripts/Makefile.build` and sources from `linux/`.

Read-only checks of `linux@c2950f0b750d` confirmed `drivers/gpu/drm/{amd,nouveau,radeon,i915,xe}` are present. The working `linux/` tree at the pinned commit also already contains the AMDGPU/Nouveau sources, their Kconfig/Makefile wiring, `include/uapi/drm/amdgpu_drm.h`, AMD DRM headers, and required shared DRM helpers. Because the action-safety contract forbids modifying `linux/`, and copying source into an output directory would not affect this build, **zero source files were restored and zero source prerequisites were added**. The generated AMD/Nouveau object trees were created by the build.

This is not version skew: the build uses the full local pinned source tree directly. The `linux/` repository was not modified.

## 5. Firmware assessment

### Probe timing and i915 reference

`CONFIG_BLK_DEV_INITRD=y` only permits an initrd; it does not create one. `CONFIG_INITRAMFS_SOURCE=""` and the distro's no-initrd boot mean no early userspace firmware filesystem exists. Built-in PCI drivers register/probe during kernel initcalls, before `prepare_namespace()` mounts the real disk root. Therefore a built-in AMDGPU request for `/lib/firmware/amdgpu/...` cannot be satisfied from the later root filesystem at first probe. “GPU is not boot-critical” does not defer the built-in PCI probe.

The current tree embeds no firmware (`CONFIG_EXTRA_FIRMWARE=""`). A search of `buildroot/` found no i915 GuC/HuC firmware payload or packaging reference. This currently works for basic Intel display because GuC/HuC are optional acceleration/media components, not a general proof that required AMD microcode can load before root mount.

### Missing-firmware behavior, checked in source

For GCN1, `gmc_v6_0_init_microcode()` requests `amdgpu/<chip>_mc.bin` as `AMDGPU_UCODE_REQUIRED`; `gfx_v6_0_init_microcode()` similarly requires PFP, ME, CE, and RLC blobs. `amdgpu_ucode_request()` maps a failed `request_firmware()` to `-ENODEV`. The GMC/GFX `sw_init` functions return that error, and `amdgpu_device_ip_init()` aborts device initialization. This is not a graceful “accelerated features off” path. The likely result is AMDGPU failing to bind while firmware/simpledrm state and userspace handoff determine whether the screen remains usable; a black screen is a credible failure mode and must be hardware-tested. Nouveau GSP lookup also propagates `-ENOENT` in its GSP firmware path.

### Measured inventory and ISO budget

No local linux-firmware checkout, `WHENCE`, or AMD firmware package is available, so an exact AMD number cannot honestly be produced offline. It requires downloading/installing the matching linux-firmware AMD package and measuring the selected files. Published/package-scale figures below are therefore explicitly approximate.

The host's locally installed NVIDIA firmware was measured:

| Set | Files/data | Bytes | MiB |
|---|---:|---:|---:|
| Entire local `/usr/lib/firmware/nvidia` | directory tree | 65,829,358 | 62.78 |
| Regular files under `nvidia/*/gsp/` | 16 files | 62,359,504 | 59.47 |
| Unique Turing GSP image (`tu102`) | one main blob | 23,750,944 | 22.65 |
| Unique Ampere/Ada GSP image (`ga102`; Ada symlinks here) | one main blob | 38,061,600 | 36.30 |

The remaining local NVIDIA tree is about 3.47 MiB and contains generation-specific ACR/GR/SEC2/NVDEC support. Turing sibling directories mostly contain small per-chip data and/or links; Ada `ad103`/`ad104`/`ad106`/`ad107` are 12-byte symlinks to the `ga102` GSP image.

For AMD GCN1 through RDNA3, ship the needed `amdgpu/*` microcode families (SI/CIK, VI/Polaris, Vega, Navi/RDNA1, Sienna/Navy/Dimgrey/Beige/RDNA2, and GC/SDMA/PSP/SMU/VCN/DMCUB blobs for RDNA3). A current full `amdgpu/` directory is approximately **80–100 MiB uncompressed**; this is an estimate, not a local measurement. A device-ID-generated allow-list could be smaller, but a broad second-hand-laptop image should not guess away families without an inventory.

**Recommended trimmed set for the 700 MiB ISO:** the complete AMD GCN1→RDNA3 subset plus the measured local NVIDIA Turing/Ampere/Ada GSP and ancillary tree, excluding datacenter-only and post-Ada families where separable. Budget approximately **143–163 MiB uncompressed** (AMD estimated 80–100 MiB + NVIDIA measured 62.78 MiB). SquashFS ISO growth will be lower but must be measured in the release build. If that is too large, prioritize AMD first, then NVIDIA Turing/Ampere based on the actual hardware census; do not ship a built-in driver without its required blobs.

## Recommendation and release gate

**NO-GO for dropping this exact `=y`, no-initramfs image into 1.0.** Source compatibility, configuration, and build size are acceptable: the kernel-side enablement costs only 5.29 MiB compressed. The blocker is deterministic firmware availability at probe, compounded by an unmeasured 80–100 MiB AMD payload and lack of hardware boot evidence.

Fastest credible route to GO:

1. Change AMDGPU and Nouveau to modules (`=m`), build/install those modules, and load them after the root filesystem (and `/lib/firmware`) is available; or add a real initramfs/embedded firmware set.
2. Acquire the pinned/current linux-firmware dataset, derive an explicit AMD GCN1→RDNA3 allow-list, and measure both raw and SquashFS contribution.
3. Boot-test at minimum one SI/CIK-era AMD, one Polaris/Vega, one RDNA2/3, one pre-GSP Nouveau, and one Turing/Ampere GSP laptop, including missing-firmware fallback behavior.

Once firmware delivery is fixed, the clean pinned-source build supports a **GO for shipping AMDGPU + Nouveau**; no kernel-source integration problem remains.
